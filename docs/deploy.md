# Деплой: почему был 502 и что из этого вышло

> Часть правил проекта. Главный файл — `AGENTS.md`; здесь подробности, которые нужны не в каждом
> разговоре, а при правке прокси, деплое и разборе «сайт не открывается».

### Почему после деплоя был 502 — и чем это закончилось (24.11.2026, измерено)

**Прошлое объяснение было неверным.** В правилах стояло: «nginx держит IP апстрима в кэше, ошибка
проходит до минуты». По факту 502 держался **около пяти минут** после каждого переключения,
и проходил только когда контейнеру возвращался **тот же IP** (`.4`).

**Настоящая причина:** `proxy_pass http://alyaeva-web:8000` без переменной. Такой nginx резолвит имя
**один раз — при старте и при reload** — и держит полученный IP навсегда. Новый контейнер получил
`.9`, а прокси полчаса стучался в `.4`: `connect() failed (113: Host is unreachable)`.

| Что сделано | Как |
|---|---|
| Правило | `proxy_pass` на приложение — **только через переменную** + `resolver 127.0.0.11 valid=10s` в `_app-proxy.inc` |
| Проверка | `docker exec proxy nginx -t` → `nginx -s reload` → `check-live.js` |
| Замер | до правки: `т+283 с → 502`; после: `т+3 с → 200` в трёх прогонах подряд |

### ЛОВУШКА: та же беда была у СТАТИКИ — не только у приложения (24.11.2026)

Приложение я перевёл на переменную, а **статику (`alyaeva-site`) забыл**: `proxy_pass http://alyaeva-site:80;`.
Каждый `docker restart alyaeva-site` (а его делает `deploy-site.js`) давал контейнеру новый IP —
и **весь сайт на минуты уходил в 502**: прокси стучался на старый `.7`, контейнер жил на `.4`.

| Что | Как |
|---|---|
| В конфиге | `set $alyaeva_static alyaeva-site;` + `proxy_pass http://$alyaeva_static:80;` |
| `resolver` | объявлен в **угловом** блоке `server` (первый), второй `server` — только `return 301` |
| Проверка | `docker restart alyaeva-site` → через 3 с главная должна быть 200 |
| Куда смотреть | `docker logs proxy` → `connect() failed (113: Host is unreachable)` и **какой IP** в строке |

**Правило:** размещённый на движке розданный адрес контейнера (hostname) в `proxy_pass` — всегда через
переменную с `resolver`, для **любого** контейнера, а не только для приложения. Проверять перезапуском
именно того контейнера, а не сайта в целом.

**Ловушка при правке:** `set $var ...; proxy_pass http://$var:8000;` работает только если `resolver`
объявлен в том же контексте (`server` или `location`), иначе `nginx -t` падает на `host not found in upstream`.

### Честно про окно простоя при деплое (владелец, 24.11.2026)

**Слова владельца:** «При обновлении сайт может упасть на пару секунд, это приемлемо, так и быть.
Вычищай старые контейнеры и ветки. Всегда подчищай за собой, чтобы мусора не оставалось».

`deploy-guarded.js` переключает имя контейнера: stop старого → rename → rename → start → подключение сетей.
Между stop и началом работы нового приложения апстрим недоступен — **единицы секунд**.
Это **не** «бесшовно»: прежняя формулировка была неточной. Но это и не простой: старый контейнер
умирает уже после того, как кандидат прошёл проверку страниц.

| Что | Значение |
|---|---|
| Окно | единицы секунд, 502 может пройти сам |
| Позволено ли | **да, владелец разрешил явно** |
| Что нельзя | останавливать прод, не проверив кандидата заранее |

### Вместо 502 человек видит «Сайт обновляется» (24.11.2026)

Владелец: «Минута 502 при обновлении сайта — устраивает? Если нет, сделаю постоянное имя».
Постоянное имя не понадобилось: проще и надёжнее — **страница-заглушка**.

| Что | Где |
|---|---|
| Страница | `build/dist/maintenance.html` → прод `E:\DockerData\alyaeva\html\maintenance.html` |
| Стиль | шапка и подвал скопированы с сайта, шрифты и цвета — токены `assets/style.css` |
| Отдаётся | статикой (`alyaeva-site`), поэтому работает, **когда приложения нет** |
| Включается | `error_page 502 503 504 = @maintenance;` у каждого `proxy_pass` на приложение |
| Настройка | named location `@maintenance` в блоке `server` для 443 |

Страница говорит «это займёт меньше минуты», даёт кнопку «Попробовать ещё раз» и телефон,
и перезагружается сама через 30 секунд (`meta refresh`).

**Проверка (обязательно делать так, а не «выглядит нормально»):**
`docker stop alyaeva-web` → `/login` и `/ceny` должны отдать **200** с текстом «Сайт обновляется»
и подключёнными стилями → `docker start alyaeva-web` → страница приложения снова 200.

**Ловушка:** `resolver` нужен в том `server`, где стоят `proxy_pass` с переменными. Я один раз
вставил его в блок `:80` (там только `return 301`) — конфиг проходил `-t`, но адреса не обновлялись.

### Почему не «обновить сайт в одном контейнере»

Код **вшит в образ** (`COPY . /app` в Dockerfile), а не смонтирован с диска. Внутри контейнера
uvicorn запущен без `--reload`. Значит правка кода требует **нового контейнера** — иначе сайт
останется на старом коде. Смонтировать каталог «чтобы только рестартовать» нельзя: в контейнере
интерпретатор и зависимости подбираются образом, а рестарт всё равно даёт те же секунды простоя.

## ОТКАТ И ПРОВЕРКА СЛИЯНИЯ (перенесено из AGENTS.md 24.11.2026)

**Откат (если прод упал).** Поднять предыдущий образ под тем же именем контейнера:
`docker rm -f alyaeva-web && docker run -d --name alyaeva-web ... <прежний image>`.
**Слияние — только после проверки ответа.** Ветку удалять, **только** когда API подтвердил слияние
(`merged === true`) и `git show main:<файл>` показывает правку. 24.11.2026 я удалил ветку,
не убедившись в слиянии: ответ был пустым, `pr.number` — `undefined`, правка осталась в удалённой
ветке. Спасло только то, что я проверил `main`. Коммит в такой ситуации не пропадает:
`git cat-file -t <sha>` → `git cherry-pick <sha>` (задача #111).

**НЕ** переименовывать контейнер через `docker rename` — старый остаётся с `--restart unless-stopped`
и бесконечно перезапускается зомби, мешая разбору.

**Проверка живости после КАЖДОГО изменения:** `node scripts\check-live.js`
(свежий контейнер, а не кэш Docker — старые тестовые контейнеры дают ложное «жив»).
