# Ошибки агента — чтобы не повторять

Записи о том, где я уже обжигался в этом проекте. Читать перед работой, писать — сразу после
того, как ошибка поймана. `AGENTS.md` короткий (бюджет инструкций), поэтому держать здесь.

## Как пользоваться

| Когда | Что |
|---|---|
| перед работой | просмотреть разделы, совпадающие с темой (deploy, nginx, проверки) |
| ошибка случилась | **в тот же заход** добавить строку: что было, почему не заметил, как проверять впредь |
| правило общее для любой задачи | короткой строкой дублировать в `AGENTS.md`, подробности оставить здесь |

Формат записи — три поля: **Что было** / **Почему не заметил** / **Как проверять**. Если третье
поле нельзя заполнить конкретной командой или запросом, запись бесполезна.

## 24.11.2026

### Возврат ответа из middleware не доходит до клиента

- **Что было:** CSRF-middleware возвращал `JSONResponse(403)` прямо из `@app.middleware("http")`.
  Отладочные печати подтверждали, что отказ сработал, `call_next` не вызывался — а клиент видел
  обычную страницу входа. Полдня ушло на файл `csrf_cookie.py`, `BaseHTTPMiddleware`, monkey-patch
  `build_middleware_stack` — всё это не работало и было удалено.
- **Почему не заметил:** проверял внутренней печатью и `call_next`, а не ответом живого сервера.
  В изолированных пробах «работало», в настоящем процессе — нет (проба падала с кодом 137).
- **Как проверять:** **всегда смотреть ответ снаружи** — `POST` запросом к контейнеру и к домену
  (статус + признак в теле). Если проверка видна только в консоли сервера — она не проверена.
  Рабочая схема: решение принимается до `call_next`, отказ возвращается обычной функцией
  (`deny_csrf(request)`), а не ответом из обёртки.

### Две одинаково правдоподобные причины отказа — одна догадка

- **Что было:** чужой `Origin` давал 403. Я по очереди «оправдал» это скрытыми глобальными
  переменными, сам внутренний процесс, разную работу `docker exec` и `http.client` — четыре
  догадки подряд, каждая через отдельный прогон.
- **Почему не заметил:** `docker exec ... python -u` при успешном прогоне возвращал код 137
  (демон убивает процесс-a), и я считал вывод ненадёжным, а не результат — истинным.
- **Как проверять:** сначала прогнать **минимальный повторяемый случай** (3–4 запроса с разным
  порядком), убедиться, что результат воспроизводится, и только потом строить объяснение.
  Код 137 после успешных строк — это про завершение контейнера, а не про ложь в выводе.

### Правка по якорю молча не применяется

- **Что было:** замена строки в `order.html` не сработала: фрагмент с кириллицей и экранированными
  кавычками не совпал. Проверка «осталось ли `₽` без фильтра» показала строку, которую я считал
  уже исправленной.
- **Почему не заметил:** делал `replace` без проверки `includes()` и без просмотра результата.
- **Как проверять:** перед заменой — `s.includes(from)`, после — распечатать изменённую строку
  (`JSON.stringify`), не полагаться на «должно было сработать».

### Проверка на живом контейнере врёт из-за мутирующих скриптов

- **Что было:** проба на копии прода делала вход и падала с 137, хотя отдельный вход в том же
  контейнере проходил. Проба, вставлявшая пользователя и сразу писавшая страницу, тоже падала.
- **Почему не заметил:** запускал всё в одном процессе — вход через приложение меняет общий пул
  соединений, а мой же код рядом открывал/закрывал его.
- **Как проверять:** в одной пробе — **одно действие**. Вход, вставка в базу, чтение страницы —
  разными процессами (`docker exec` по очереди), а не одним скриптом.

### Заголовок задачи и карта устаревают молча

- **Что было:** после закрытия #164 карта и заголовок #166 продолжали показывать старые цифры
  (207 стилей, когда осталось 142).
- **Почему не заметил:** правил задачу, но не тело и не карту.
- **Как проверять:** закрывая задачу — сразу обновить **заголовок**, **тело** и строку в карте #23;
  проверять `grep` по номеру в теле карты.

### Счёт бюджета инструкций: считать оба файла

- **Что было:** считал только проектный `AGENTS.md` и закрыл #164, хотя бюджет 65 536 — на всё,
  включая глобальный `$DSH_HOME/AGENTS.md` (28 533). Вместе 86 618 — харнесс выкидывал файл.
- **Почему не заметил:** в задаче был приведён только размер проектного файла.
- **Как проверять:** перед выводом «влезает» — сложить оба файла и сравнить с 65 536.

### Удаление ветки: локальное и серверное — разные команды

- **Что было:** `git push origin --delete` несколько раз ответил `remote ref does not exist`, но
  ветка на GitHub оставалась живой.
- **Как проверять:** удалять через API (`DELETE /git/refs/heads/<ветка>`) и проверять `404`
  после; локальную ветку — отдельно `git branch -D`.

### Мои же проверки оставляют следы в данных

- **Что было:** один прогон `smoke.js` под админом и мои `POST`-запросы набирают десятки событий
  в `site_events` и сессии. Заголовок `X-DSH-Check: 1` глушит **только** `/api/visited`.
- **Как проверять:** после проверок — `SELECT` по `site_events` и `sessions` за точный отрезок
  времени и `DELETE` только своего; тестовых пользователей искать по `email LIKE 'probe%'`.

### Клон контейнера показывает чужой сайт

- **Что было:** проба `docker run --network container:alyaeva-web` показывала старые страницы и старый
  `app.css`, хотя собранный образ содержал новые файлы (6 346 байт шаблона, `style=` 0). Полчаса ушло
  на версии про слои Docker и кэш сборки — а причина в проверке: в общем netns порт 8000 уже занят
  приложением прода, свой `uvicorn` падает с `address already in use`, а проба читает ответ старого.
- **Почему не заметил:** не смотрел `docker logs` клона и не ждал готовности именно своего процесса.
- **Как проверять:** перед пробой — `docker logs` клона и ожидание `/health` с таймаутом, а файлы внутри
  образа смотреть `docker run --entrypoint sh <образ> -c "..."`, а не через страницу клона.
### Проверка кандидата: рабочая схема, а не хвост от прода

- **Что было:** проба через `--network container:alyaeva-web` (общий netns) читает ответ **прода**: порт
  8000 уже занят, свой `uvicorn` падает с `address already in use`. Страница выглядит старой, а файлы
  в образе новые — вывод «сборка не применяется» ложный.
- **Почему не заметил:** не смотрел `docker logs` клона и не ждал готовности своего процесса.
- **Как проверять (проверено 24.11.2026):** кандидата поднимать в сети с базой (`sc-stand-main_net`),
  с `--env-file E:/DockerData/alyaeva/.env`, под именем **`app-cand`**, ждать строку `Application startup complete`
  в `docker logs`; пробу гонять из второго контейнера **в той же сети**, обращаясь к `http://app-cand:8000`.
  Алиас имени у прода (`alyaeva-web`) не трогать: клон без алиаса сосуществует рядом.
