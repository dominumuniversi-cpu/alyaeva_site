## Железные правила

**Только alyaeva.pro.** Единственное пересечение с другими проектами — общий контейнер `proxy` (nginx, 80/443).
Чужие стенды, контейнеры, адреса, конфиги и логи — не моя зона: не смотреть, не проверять, не упоминать в отчётах.
Проверка после работы — только своё: `check-live.js`, `/static/app.css` = 200, `docker exec proxy nginx -t`.

**Сайт не ронять.** Любые работы — только бесшовно. Перезапуск контейнера = простой.

- Перед работой и после неё: `node scripts\check-live.js` (должно быть 200 и серт валиден)
- Продление сертификата трогает `proxy` только если до истечения ≤30 дней
- Тексты/конфиги применяются через `docker restart alyaeva-site` (контейнер без портов, перезапуск 2–3 сек — не роняет сайт)

## Особенности этой машины (DIMAS)

**PowerShell 5.1 не запускает внешние процессы** в среде агента: `& docker.exe version` возвращает пустоту и код 0.
Поэтому: **вся автоматизация — на Node.js**. PowerShell годится только как лаунчер `node.exe` в планировщике.

Заодно два старых грабля:
- `.ps1` писать **только в UTF-8 с BOM**, иначе PS 5.1 читает как ANSI и ломает кириллицу
- docker пишет в stderr; при `ErrorActionPreference=Stop` это NativeCommandError — проверять `$LASTEXITCODE`

## ПОЧЕМУ САЙТ «НЕ РАБОТАЕТ», ХОТЯ 200 (23.11.2026)

Владелец трижды писал «сайт не работает», а curl снаружи отдавал 200. Разбор:

| Симптом | Причина | Что делать |
|---|---|---|
| `http://alyaeva.pro` → **403** «Server: Web server», `X-Detail: 0x1210 insufficient security level` | отвечает **оборудование провайдера**, не наш nginx. Порт 80 перехвачен снаружи | только `https://`. Обучить владельца: без «s» не откроется никогда |
| `ERR_CONNECTION_CLOSED` | браузер шёл по http, либо HSTS/стейплинг | снят `includeSubDomains; preload` из HSTS (ломал www и поддомены), убран мёртвый `ssl_stapling` (у LE нет OCSP URL) |

**Приём:** «сайт не работает» — НЕ повод бежать чинить. Сначала выяснить, ЧТО именно открывает человек:
`http` или `https`, имя или IP. Смотреть `docker logs proxy` и искать строку с его User-Agent —
там видно истинный код ответа (404/403/502). Несколько раз причиной был http от провайдера, а сайт всё это время работал.


## ПОЛИТИКА HTTPS — сайт живёт только на 443 (владелец, 23.11.2026)

**Правило:** HTTP не нужен. Всё обслуживается по HTTPS, порт 80 нужен ровно для одной вещи —
вернуть человека, который набрал адрес без «s», на HTTPS (301). Никакого контента на 80 нет.

| Что | Статус |
|---|---|
| Блок `listen 80` | `return 301 https://$host$request_uri` — контента нет, только редирект |
| Снаружи порт 80 | **перехвачен оборудованием провайдера** (`Server: Web server`, `X-Detail: 0x1210`), наш nginx запроса не видит |
| Защита от «открыл по http» без порта 80 | **HSTS** `max-age=31536000` — браузер после первого HTTPS-захода сам переписывает http→https |

**HSTS без `includeSubDomains; preload`** — намеренно: с этими флагами ломался `www`
(у него отдельный серт). Не возвращать.

**Приём для владельца:** если в браузере `http://` — это не наш сайт, а провайдер.
Проверка за 1 команду: `curl -sI http://alyaeva.pro` → `Server: Web server` = провайдер, `nginx` = мы.

## СТИЛИСТИКА: каждая страница приложения — в стиле сайта (владелец, 23.11.2026)

**Требование владельца:** админка, кабинет, вход, регистрация, заказ — всё в общей стилистике сайта.

### Токены (один в один как `E:\DockerData\alyaeva\html\assets\style.css`)

```
--c-accent:#4B4690  --c-strong:#2A2650  --c-body:#4A4678
--c-cream:#FFF1C7   --c-peach:#FFEBE0   --c-lilac:#E6DFFA   --c-mint:#EAF7F4

```

### ЛОВУШКА, из-за которой /login год был без стилей

nginx проверяет регулярки (`location ~* \\.(css|js)$`) **РАНЬШЕ** префиксов.
Поэтому `/static/app.css` уходил в `alyaeva-site` (404), хотя `location /static/` был прописан.

**Лечение:** `location ^~ /static/` — префикс с `^~` имеет приоритет над регулярками.
**Запомнить:** `location /static/` и `location ~* \\.css$` вместе = регулярка победит.

### Правило проверки

«Страница отдаёт 200» ≠ «страница выглядит нормально». Проверять **CSS-файл отдельно**:
`curl -o /dev/null -w '%{http_code}' https://alyaeva.pro/static/app.css` → должно быть 200.
200 на странице + 404 на css = страница без стилей.

Как проверять — раздел «ПРОВЕРКА СТИЛЕЙ» ниже.

### Все страницы приложения наследуют base.html

`base.html` даёт шапку (логотип, навигация) и подключение `/static/app.css`.
Новая страница = `{% extends "base.html" %}` + `{% block content %}`. Свой `<html>` не писать.


## ЗАКАЗ — ТОЛЬКО ДЛЯ ВОШЕДШИХ (владелец, 23.11.2026)

**Требование:** авторизованный идёт на страницу заказа; неавторизованному предлагаем войти и
после входа возвращаем **к заказу**, а не в кабинет.

### Как устроено

| Шаг | Что происходит |
|---|---|
| Гость → `/order` | `303` на `/login?next=/order&reason=order` |
| Страница входа | заголовок «Войдите, чтобы заказать» + скрытое поле `next` |
| Вход / регистрация | возврат на `_safe_next(next, "/cabinet")` |
| `POST /api/order` | без сессии → `401` + `{"login": true}`, JS уводит на вход |
| Загрузка фото | требует сессии, проверяет владельца (403 на чужой заказ) |

### Два правила, которые нельзя нарушать

1. **`_safe_next()`** — только внутренние пути (`/`-префикс, не `//`, без `\\`). Иначе это открытый редирект.
2. **Номер заказа НЕ ключ доступа.** Номера предсказуемы (`AA-261123-001`), раньше гость по номеру
   мог грузить фото в чужой заказ. Теперь номер ничего не даёт без сессии.

### Проверено (5 сценариев + 5 попыток обхода)

гость→вход 303 ✓ · вход с next→/order ✓ · регистрация с next→/order ✓ · без next→/cabinet ✓ ·
`next=//evil.com`, `/\\evil.com`, `https://evil.com`, `javascript:` → всё на /cabinet ✓

## ЛОВУШКА: метод не совпал — 405 «Method Not Allowed» (23.11.2026)

Владелец открыл `/logout` и получил `{"detail":"Method Not Allowed"}`.

**Причина:** обработчик объявлен только как `@app.post("/logout")`, а ссылка в меню — `<a href="/logout">`,
то есть обычный **GET**. FastAPI отвечает 405.

**Правило:** если на действие ведёт ссылка из меню — вешать **оба** декоратора:

    @app.get("/logout")
    @app.post("/logout")
    def logout(request: Request): ...

Или делать кнопку с формой (тогда только POST). Но не оставлять разрыв.

**Проверять** действие не только «глазами», а запросом того метода, который реально шлёт браузер:
`curl -D- -o /dev/null https://alyaeva.pro/logout` → должно быть 303, а не 405.

## КАЖДЫЙ МАРШРУТ ПРИЛОЖЕНИЯ — В NGINX ВРУЧНУЮ (23.11.2026)

Маршруты приложения в `alyaeva.pro.conf` прописаны **по одному**: `/login`, `/register`, `/order`,
`/cabinet`, `/logout`, `/settings`, `/api/`, `/health`, `/6b03c5256535e9ab5a`, `/static/`.

**Добавил страницу в FastAPI — добавь `location` в vhost, иначе 404.**
Именно так `/settings` отдавал 404 после деплоя, хотя в приложении всё работало.

**Порядок:**
1. быстрое исправление — `location /settings { proxy_pass http://alyaeva-web:8000; include /etc/nginx/vhosts/_app-proxy.inc; }`
2. **обязательно** `docker exec proxy nginx -t` → потом `nginx -s reload`
3. проверять на проде **тем адресом, который откроет человек** (не только изнутри сети)

```
docker exec proxy nginx -t && docker exec proxy nginx -s reload
curl -s -o /dev/null -w '%{http_code}' https://alyaeva.pro/settings   # 200, не 404
```

## СТРАНИЦЫ ОШИБОК: человеку — страница, скрипту — JSON (23.11.2026)

**Правило владельца:** «Каждая страница должна обрабатываться. Если не найдена — 404.
Если уже залогинены, но писать, что доступ запрещён — тоже отдельная страница.
Правило одинаковое для всех страниц, не только для hooks.»

| Заголовок Accept | Ответ |
|---|---|
| `text/html` (браузер) | **страница**: 404.html / 403.html / hook_landing.html |
| `*/*` или `application/json` (curl, fetch, бот) | **JSON** |

**Решаем по Accept, НЕ по пути.** Раньше всё под `/api/` и `/hooks/` безусловно
отдавало JSON — и владелец видел `{"detail":"Not Found"}` живыми глазами.

**Ловушка:** curl по умолчанию присылает `Accept: */*` — как и fetch. Поэтому
страницу даём **только** при явном `text/html`, иначе скрипты получат HTML.

**Где что:**
- `main.py` → `_wants_json()` + `@app.exception_handler` для 403/404/405/422
- `web_common.denied()` → единый отказ: страница человеку, JSON скрипту
- `admin_only()` / `_deny()` → не залогинен: на вход с `next`; залогинен без прав: **403-страница**, не молчаливый редирект

**Проверять:** один и тот же адрес с `-H 'Accept: text/html'` и с `*/*` — должны дать страницу и JSON.

## ПРОВЕРЯТЬ ВХОД БРАУЗЕРОМ, А НЕ CURL (24.11.2026)

Cookie `sid` выдаётся с флагом `Secure`. На стенде по http **браузер её молча выбрасывает**,
а `curl -H 'Cookie: ...'` — нет. Поэтому curl «входил», а живой человек не мог.

- Флаг из окружения: `COOKIE_SECURE` (по умолчанию 1). Прод — не задавать (https).
- Стенд: `docker run -e COOKIE_SECURE=0 ...`
- Сценарии входа проверять puppeteer'ом, иначе сквозной дефект не виден.
