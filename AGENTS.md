# alyaeva.pro — правила работы

## Проект

Сайт-визитка Алёны Аляевой (Екатеринбург): именные книги для детей с фото, фотокниги.
Живой прод: **https://alyaeva.pro**. Работы идут НА ЖИВОМ сайте.

## Железные правила

**Сайт не ронять.** Любые работы — только бесшовно. Перезапуск контейнера = простой.

- Перед работой и после неё: `node scripts\check-live.js` (должно быть 200 и серт валиден)
- Продление сертификата трогает `proxy` только если до истечения ≤30 дней
- Тексты/конфиги применяются через `docker restart alyaeva-site` (контейнер без портов, перезапуск 2–3 сек — не роняет сайт)

## Особенности этой машины (DIMAS)

**PowerShell 5.1 не запускает внешние процессы** в среде агента: `& docker.exe version` возвращает пустоту и код 0.
Поэтому: **вся автоматизация — на Node.js**. PowerShell годится только как лаунчер `node.exe` в планировщике.

Заодно два старых грабля:
- `.ps1` писать **только в UTF-8 с BOM**, иначе PS 5.1 читает как ANSI и ломает кириллицу
- docker пишет в stderr; при `ErrorActionPreference=Stop` это NativeCommandError — проверять `$LASTEXITCODE`

## Ветки и деплой (правило владельца, 23.11.2026)

**main — только то, что работает на проде. Прямых коммитов в main нет.**

| Правило | Как |
|---|---|
| Доработки | отдельная ветка на каждую задачу: `feat/<тема>`, `fix/<тема>`, `chore/<тема>` |
| Ветка от | всегда актуального `main` |
| Слияние | только PR в `main` после проверки |
| Деплой | **CI/CD деплоит с `main`**, а не с веток |

Почему так: ломать прод из ветки нельзя — сначала проверка, потом слияние, потом автодеплой.

**Откат (если прод упал).** Поднять предыдущий образ под тем же именем контейнера:
`docker rm -f alyaeva-web && docker run -d --name alyaeva-web ... <прежний image>`.
**НЕ** переименовывать контейнер через `docker rename` — старый остаётся с `--restart unless-stopped`
и бесконечно перезапускается зомби, мешая разбору.

**Проверка живости после КАЖДОГО изменения:** `node scripts\check-live.js`
(свежий контейнер, а не кэш Docker — старые тестовые контейнеры дают ложное «жив»).


## НЕ говорить «вы отклонили» — это неправда (23.11.2026)

Сообщение `the user rejected tool "X"` **не значит**, что пользователь что-то отклонял.
В `@deepseek-ai/dsh-user-approval/lib/index.js`: если политика сессии `"never"`, сразу возвращается
`"rejected"`, а вызывающий код превращает это в «пользователь отклонил». Запроса к человеку не было.

**Правильно говорить:** «в этой сессии подтверждения отключены, запрос до вас не дошёл».
Не приписывать решение владельцу, пока он сам не подтвердил.


## ПОЧЕМУ САЙТ «НЕ РАБОТАЕТ», ХОТЯ 200 (23.11.2026)

Владелец трижды писал «сайт не работает», а curl снаружи отдавал 200. Разбор:

| Симптом | Причина | Что делать |
|---|---|---|
| `http://alyaeva.pro` → **403** «Server: Web server», `X-Detail: 0x1210 insufficient security level` | отвечает **оборудование провайдера**, не наш nginx. Порт 80 перехвачен снаружи | только `https://`. Обучить владельца: без «s» не откроется никогда |
| `https://188.226.71.169/` → 404 | это **наш собственный** default_server (registry/стенды), туда нет маршрута сайта | заходить по имени домена, не по IP |
| `ERR_CONNECTION_CLOSED` | браузер шёл по http, либо HSTS/стейплинг | снят `includeSubDomains; preload` из HSTS (ломал www и поддомены), убран мёртвый `ssl_stapling` (у LE нет OCSP URL) |

**Приём:** «сайт не работает» — НЕ повод бежать чинить. Сначала выяснить, ЧТО именно открывает человек:
`http` или `https`, имя или IP. Смотреть `docker logs proxy` и искать строку с его User-Agent —
там видно истинный код ответа (404/403/502). Несколько раз причиной был http от провайдера, а сайт всё это время работал.


## ПОЛИТИКА HTTPS — сайт живёт только на 443 (владелец, 23.11.2026)

**Правило:** HTTP не нужен. Всё обслуживается по HTTPS, порт 80 нужен ровно для одной вещи —
вернуть человека, который набрал адрес без «s», на HTTPS (301). Никакого контента на 80 нет.

| Что | Статус |
|---|---|
| Блок `listen 80` | `return 301 https://$host$request_uri` — контента нет, только редирект |
| Снаружи порт 80 | **перехвачен оборудованием провайдера** (`Server: Web server`, `X-Detail: 0x1210`), наш nginx запроса не видит |
| Защита от «открыл по http» без порта 80 | **HSTS** `max-age=31536000` — браузер после первого HTTPS-захода сам переписывает http→https |

**HSTS без `includeSubDomains; preload`** — намеренно: с этими флагами ломался `www`
(у него отдельный серт). Не возвращать.

**Приём для владельца:** если в браузере `http://` — это не наш сайт, а провайдер.
Проверка за 1 команду: `curl -sI http://alyaeva.pro` → `Server: Web server` = провайдер, `nginx` = мы.


### ЛОВУШКА, из-за которой /login год был без стилей

nginx проверяет регулярки (`location ~* \\.(css|js)$`) **РАНЬШЕ** префиксов.
Поэтому `/static/app.css` уходил в `alyaeva-site` (404), хотя `location /static/` был прописан.

**Лечение:** `location ^~ /static/` — префикс с `^~` имеет приоритет над регулярками.
**Запомнить:** `location /static/` и `location ~* \\.css$` вместе = регулярка победит.

### Правило проверки

«Страница отдаёт 200» ≠ «страница выглядит нормально». Проверять **CSS-файл отдельно**:
`curl -o /dev/null -w '%{http_code}' https://alyaeva.pro/static/app.css` → должно быть 200.
200 на странице + 404 на css = страница без стилей.

Скрипт проверки — задача #17 (headless-браузер, блокирует CI).

### Все страницы приложения наследуют base.html

`base.html` даёт шапку (логотип, навигация) и подключение `/static/app.css`.
Новая страница = `{% extends "base.html" %}` + `{% block content %}`. Свой `<html>` не писать.
